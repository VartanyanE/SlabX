# PostgreSQL Database Design

## 1. Conventions

- PostgreSQL 18, UTC `timestamptz`, and UUIDv7 primary keys generated by the application/database.
- Table and column names use `snake_case`; application types use `PascalCase`/`camelCase`.
- Money uses `bigint` minor units plus a three-character ISO currency code. Never use floating point.
- Mutable records have `created_at`, `updated_at`, and an integer `version` for optimistic concurrency where useful.
- Soft deletion is selective: user content and catalog/listings may use `deleted_at`; financial, order, payment, shipment, dispute, webhook, and audit records are retained and status-closed.
- Enums are represented by PostgreSQL enums or constrained text according to migration needs. State transitions are enforced in application services and tested; critical uniqueness is enforced in the database.
- Personally identifiable information and secrets are encrypted or tokenized where required. Logs never contain credential hashes, full addresses, tokens, or raw provider payloads with sensitive data.

## 2. Identity and profile

### `users`

`id`, `email_normalized`, `email_display`, `email_verified_at`, `status`, `last_login_at`, timestamps, `deleted_at`.

- Unique: `email_normalized` where not deleted
- Status: `PENDING_VERIFICATION`, `ACTIVE`, `SUSPENDED`, `CLOSED`
- Index: `(status, created_at)`

### `password_credentials`

`user_id` PK/FK, `password_hash`, `password_changed_at`, `failed_attempts`, `locked_until`.

No plaintext or reversible password data.

### `auth_identities`

`id`, `user_id`, `provider`, `provider_subject`, `provider_email`, timestamps.

- Unique: `(provider, provider_subject)`
- Index: `user_id`
- Provider initially `GOOGLE`; password identity remains in `password_credentials`.

### `sessions`

`id`, `user_id`, `token_hash`, `expires_at`, `last_seen_at`, `revoked_at`, `ip_hash`, `user_agent_hash`, timestamps.

- Unique: `token_hash`
- Indexes: `(user_id, revoked_at)`, `expires_at`

### `email_tokens`

`id`, `user_id`, `type`, `token_hash`, `expires_at`, `consumed_at`, timestamps.

- Types: verification, password reset, email change
- Unique: `token_hash`

### `profiles`

`user_id` PK/FK, unique `handle_normalized`, `handle_display`, `display_name`, `bio`, `avatar_asset_id`, `seller_status`, rating aggregates, timestamps.

### `addresses`

`id`, `user_id`, `label`, encrypted/controlled address fields, `country_code`, `is_default_shipping`, provider verification metadata, timestamps, `deleted_at`.

- Partial unique: one default shipping address per user
- Never mutate an order's address snapshot when this row changes.

### RBAC

`roles`, `permissions`, `role_permissions`, `user_roles` with unique join constraints. Start with `USER`, `SUPPORT`, `TRUST_SAFETY`, `FINANCE`, and `ADMIN` roles.

## 3. Catalog

### `categories`

`id`, unique `slug`, `name`, optional `parent_id`, `kind`, `attributes_schema` JSONB, `active`, `sort_order`, timestamps.

Category examples are data: basketball, baseball, football, pokemon. `attributes_schema` is for category-specific optional attributes, not common searchable fields.

### `manufacturers`, `card_sets`

- `manufacturers`: `id`, unique normalized name, display name
- `card_sets`: `id`, `category_id`, `manufacturer_id`, `name`, `year_start`, `year_end`, timestamps
- Unique candidate: `(category_id, manufacturer_id, normalized_name, year_start)`

### `catalog_cards`

`id`, `category_id`, `card_set_id`, `player_or_character`, `year`, `card_number`, `subset`, `variant`, `language_code`, booleans for rookie/autograph/memorabilia, `serial_total`, extensible `attributes` JSONB, `status`, `created_by_user_id`, timestamps, `deleted_at`.

- Status: `PENDING_REVIEW`, `ACTIVE`, `MERGED`, `REJECTED`
- Indexes: category, set, year, normalized player/character, card number, status
- Search: generated `tsvector` plus trigram indexes for names/set/card number
- Duplicate prevention uses normalized fingerprint plus moderation; a merged record references canonical `merged_into_id`.

### `grading_companies`

`id`, unique `code`, `name`, `grade_scale` JSONB, `cert_verification_url_template`, `active`, timestamps.

PSA, BGS, CGC, and SGC are seed data, not enums.

## 4. Collection and media

### `collection_items`

`id`, `owner_user_id`, `catalog_card_id`, `condition_type`, `raw_condition`, `grading_company_id`, `grade`, `certification_number`, `item_notes`, `visibility`, `availability_status`, acquisition fields, `version`, timestamps, `deleted_at`.

- Condition type: `RAW`, `GRADED`
- Check: raw items have no grading fields; graded items require company, grade, and certification number
- Availability: `AVAILABLE`, `LISTED`, `RESERVED`, `SOLD`, `TRADE_LOCKED`, `NOT_FOR_SALE`
- Unique candidate: `(grading_company_id, certification_number)` where graded and not deleted; exceptions require admin review
- Indexes: owner/status, catalog card, grading company/certification

### `media_assets`

`id`, `owner_user_id`, provider, provider asset ID, MIME type, bytes, width, height, SHA-256, moderation status, timestamps, `deleted_at`.

- Unique: `(provider, provider_asset_id)`
- Unique/dedup candidate: `sha256`

### `collection_item_images`

`id`, `collection_item_id`, `media_asset_id`, `sort_order`, `image_role`, timestamps.

- Unique: `(collection_item_id, media_asset_id)` and `(collection_item_id, sort_order)`
- Partial unique: one `PRIMARY` image per item

## 5. Listings and watchlists

### `listings`

`id`, `seller_user_id`, `collection_item_id`, `status`, `price_minor`, `currency`, `accepts_offers`, `minimum_offer_minor`, `published_at`, `reserved_by_user_id`, `reserved_until`, `reservation_reason`, `version`, timestamps, `deleted_at`.

- Check: positive price; minimum offer positive and not above price when present
- Partial unique: one listing in `DRAFT`, `ACTIVE`, `PAUSED`, or `RESERVED` per collection item
- Indexes: `(status, published_at desc)`, seller/status, price, item
- Search joins a denormalized `listing_search_documents` projection maintained transactionally/outbox.

Listing images normally come from item images. If listing-specific ordering/captions are required, use `listing_images(listing_id, media_asset_id, sort_order, caption)`.

### `watchlist_entries`

`user_id`, `listing_id`, `created_at`.

- Composite PK/unique `(user_id, listing_id)`

## 6. Offers

### `offer_threads`

`id`, `listing_id`, `buyer_user_id`, `seller_user_id`, `status`, `current_revision_id`, timestamps.

- Partial unique: one open thread per `(listing_id, buyer_user_id)`
- Status: `OPEN`, `ACCEPTED`, `DECLINED`, `CANCELLED`, `EXPIRED`, `CONVERTED`

### `offer_revisions`

`id`, `thread_id`, `sequence`, `created_by_user_id`, `recipient_user_id`, `amount_minor`, `currency`, `message`, `status`, `expires_at`, `responded_at`, timestamps.

- Unique `(thread_id, sequence)`
- Only one `PENDING` revision per thread (partial unique)
- Status: `PENDING`, `ACCEPTED`, `DECLINED`, `COUNTERED`, `CANCELLED`, `EXPIRED`
- Revisions are immutable after response.

## 7. Orders and finance

### `orders`

`id`, human-readable unique `order_number`, buyer/seller IDs, `status`, currency, subtotal/shipping/tax/fee/discount/total minor units, reservation expiry, provider IDs, `version`, timestamps, completed/cancelled timestamps.

- Checks ensure components are nonnegative and total equation is valid
- Indexes: buyer/created, seller/created, status/updated

### `order_items`

`id`, `order_id`, `listing_id`, `collection_item_id`, quantity fixed to 1 for MVP, unit/subtotal minor, and JSONB snapshots for catalog/item/listing evidence.

- Unique `listing_id` and `collection_item_id` for successfully paid/non-cancelled orders using partial indexes

### `order_address_snapshots`

`id`, `order_id`, `type`, encrypted address snapshot fields, timestamps. Type: `SHIP_TO`, `SHIP_FROM`, `RETURN_TO`.

### `payment_attempts`

`id`, `order_id`, provider, unique provider payment ID, unique idempotency key, status, amount/currency, failure code, timestamps.

Status: `CREATED`, `REQUIRES_ACTION`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `CANCELLED`.

### `refunds`

`id`, `order_id`, `payment_attempt_id`, provider refund ID, idempotency key, amount/currency, reason, status, initiated_by_user_id, timestamps.

### `transfers` and `payout_records`

- `transfers`: platform-to-connected-account amounts, fee linkage, provider transfer ID, reversal state
- `payout_records`: mirror seller-account payouts for support/reconciliation; Stripe remains authoritative
- Unique provider IDs and explicit currency/amount on every row

### `ledger_entries`

Append-only double-entry ledger: `transaction_id`, `account_code`, debit/credit minor units, currency, reference type/ID, timestamp. Debits equal credits per transaction. Use for platform financial reconciliation, not as a replacement for Stripe records.

## 8. Shipping and reputation

### `shipments`

`id`, `order_id`, provider shipment/rate/tracker IDs, status, carrier, service, tracking code, postage/insurance minor units, label asset URL, purchased_at, shipped_at, delivered_at, timestamps.

- Unique provider IDs and tracking code where appropriate
- One outbound shipment per MVP order; schema permits returns separately via `direction`

### `tracking_events`

`id`, `shipment_id`, unique provider event/fingerprint, status, description, location JSONB, occurred_at, received_at.

### `reviews`

`id`, `order_id`, `author_user_id`, `subject_user_id`, `role`, rating 1–5, comment, moderation status, timestamps, `deleted_at`.

- Unique `(order_id, author_user_id, role)`
- Check author differs from subject and order relationship is verified

## 9. Notifications, disputes, and audit

### `notifications`

`id`, `user_id`, type, title, body, action URL, deduplication key, read_at, timestamps.

- Unique `(user_id, deduplication_key)` when present
- Index `(user_id, read_at, created_at desc)`

### `reports` and `disputes`

- `reports`: reporter, target type/ID, reason, evidence, status, assignee
- `disputes`: order, opened_by, reason, status, resolution, financial hold metadata, timestamps
- `dispute_evidence`: dispute, submitter, media/text, timestamps
- Status histories are append-only.

### `audit_logs`

Append-only `id`, actor user/session, action, target type/ID, before/after redacted JSONB, reason, IP/user-agent hashes, correlation ID, timestamp.

No update/delete permission for the normal application role.

### `webhook_events`

`id`, provider, provider_event_id, payload_hash, event_type, received_at, processing status, attempts, processed_at, last_error.

- Unique `(provider, provider_event_id)`
- Payload retention is minimized/redacted according to policy.

### `outbox_events`

`id`, aggregate type/ID, event type, payload JSONB, created_at, available_at, attempts, processed_at, last_error.

Index pending events by `(processed_at, available_at)`.

## 10. Future trading

### `trade_threads`, `trade_revisions`

Parties and immutable proposal/counter revisions with current revision pointer and lifecycle state.

### `trade_item_components`

`trade_revision_id`, `collection_item_id`, `offered_by_user_id`, `requested_from_user_id`.

- Unique `(trade_revision_id, collection_item_id)`
- Accepted trade locking checks current ownership and availability under row locks.

### `trade_cash_components`

`trade_revision_id`, `payer_user_id`, `recipient_user_id`, `amount_minor`, `currency`.

At most one directional cash component per revision for MVP trading. Payment success must precede atomic ownership transfer.

### `item_locks`

`id`, `collection_item_id`, lock type, reference type/ID, expires_at, timestamps.

- Partial unique one active lock per item
- Listing reservations and accepted trades use the same lock abstraction when trading is implemented.

## 11. Migration and integrity policy

- Every schema change is a reviewed migration with forward and rollback/mitigation notes.
- Production destructive changes use expand/backfill/verify/contract releases.
- Seed only reference data; never seed production users or financial data.
- Nightly integrity checks cover orphan references, state mismatches, ledger balance, duplicate active locks, and provider reconciliation.
