# Staging Deployment

SlabX staging is defined by the root `render.yaml` Blueprint. It creates an isolated API, web proxy, worker, and PostgreSQL database in Render's Oregon region.

## Before creating the Blueprint

The Blueprint creates paid `starter` API and worker services plus a `basic-256mb` PostgreSQL database. Review Render's current estimate before confirming creation. The web service uses the free plan.

Use provider sandbox/test credentials only. Never paste credentials into this file, GitHub, tickets, screenshots, or logs.

## Initial Blueprint values

Render prompts for every variable marked `sync: false`:

- `WEB_ORIGIN`: the final HTTPS URL of `slabx-staging-web`
- `API_ORIGIN`: use the same web URL because `/api` is privately proxied
- `GOOGLE_CALLBACK_URL`: `<WEB_ORIGIN>/api/v1/auth/google/callback`
- Google OAuth staging client ID and secret
- Resend API key
- Cloudinary staging credentials
- Stripe test secret and staging webhook secret
- EasyPost test API key and staging webhook secret

`SESSION_SECRET` and `PASSWORD_PEPPER` are generated by Render. `DATABASE_URL` and the internal API proxy address are wired from private Render resources.

## Provider callbacks

After Render assigns the web URL, configure:

- Google authorized origin: the web origin without a trailing slash
- Google redirect URI: the full `GOOGLE_CALLBACK_URL`
- Stripe webhook: `<WEB_ORIGIN>/api/v1/payments/stripe/webhook`
- EasyPost webhook: `<WEB_ORIGIN>/api/v1/shipping/easypost/webhook`

Use newly generated webhook secrets for staging.

## Release verification

1. Confirm API liveness and readiness through the web URL.
2. Register and verify a synthetic user, then test password and Google login.
3. Create a catalog item, upload images, and publish a listing.
4. Complete a Stripe test purchase and verify the balanced ledger.
5. Buy an EasyPost test label and process tracking updates.
6. Complete review, report, refund, dispute, transfer, and payout test cases.
7. Run the load smoke against the web origin and record results.
8. Perform the backup/restore and rollback drills from the production runbook.

Do not seed production. Staging may use only deterministic synthetic data.

The staging API pre-deploy command runs the idempotent reference-data seed after
migrations. Production-mode seeding is rejected unless the deployment explicitly
sets `DATABASE_SEED_ALLOWED=true`; this opt-in belongs only on staging services.
